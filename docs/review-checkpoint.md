# 记忆整理提交中断后的本地恢复

2026-10-31。更新项目自己的 `scripts/activity_gate.py`，应用保持 1.14.3、记忆适配器保持 1.6.9。没有新增界面、任务或模型调用，不修改 Hermes 上游。

## 复现的问题

原来的 commit 依次写游标、快照完成时间、任务租约状态。这不是一个多文件事务。在隔离的虚构目录中，注入“游标已成功写入，快照文件写入失败”，旧版会抛错，但来源已经不再待整理，快照却仍未完成。CLI 的统一报错还会错误断言游标没有变化。

这是故障注入复现，不代表本机实际发生过这次事故。当前真实游标没有待恢复凭据；已有未完成快照不能仅凭文件存在就推断已整理，不做猜测式补交。

## 提交与收尾分开

仍使用现有跨进程锁和 JSON 文件，不增加数据库或消息队列：

1. 核对快照、所有当前来源版本、完整对话来源的交付记录，以及报告里的整行 `Review-Snapshot: 完整编号`。
2. 在同一次游标文件替换中，保存已消费版本与一份临时 `_pending_commit` 完成凭据。这是提交点。凭据包含快照元数据、时间、报告相对路径和字节哈希，不包含对话原文。
3. 据此幂等补齐快照完成时间，清除仅属于本快照的租约，最后去掉临时凭据。无关游标字段、新租约和其他任务状态保留。

完成凭据必须与来源清单编号及游标里的已消费版本相符；遇到冲突、未知版本或损坏时保留现场，停止新的模型唤醒，不擅自覆盖。恢复只补元数据，不重读或重演人格反馈、核心记忆修改。提交后来源被更正，新的版本仍会进入后续待整理批次；报告或旧来源随后删除，也不会通过恢复重新造回内容。

写入成功、但收尾失败时，commit 仍返回 `ok=true`，同时以 `cleanup_pending=true` 表示收尾可能尚待核对。原任务已有“ok=true 后结束”的协议，因此无需改任务提示。下次记忆预检在租约、额度和新批次判断之前尝试本地恢复；重复相同 commit 也能安全收尾。即使一次预检恢复失败，也保留旧租约关联，供下次只清除匹配的租约。

若写入报错又无法读回确认，CLI 返回 `ok=false, commit_state=unconfirmed` 和非零退出码，不再断言游标未变；应核对或重试同一个 commit，不重复追加人格反馈或自行回滚游标。暂停后台时不恢复，dry-run 不写入。这里没有强制中断模型的新规则。

## 参考与保证范围

借鉴了 [AWS transactional outbox 说明](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) 中“业务状态与后续处理意图一起保存，再幂等完成后续动作”的思路，没有采用或复制其云服务实现。

单文件替换沿用同目录临时文件和 `Path.replace`；[Python 官方说明](https://docs.python.org/3/library/os.html#os.replace) 规定成功的同文件系统替换是原子的。这里验证的是进程中断与单步 I/O 异常恢复，没有新增 fsync 或声称断电持久性；核心记忆、人格反馈和来源数据库仍在提交之前各自写入，不因此成为一个整体事务。完成凭据也不是模型确实理解每条来源的证明。

## 验证与本机生效

`python3 -m unittest discover -s scripts -p 'test_*.py'`：357 项通过，其中新增 21 项提交恢复检查，覆盖：

- 提交点前失败、提交点后各次写入失败，以及实际替换后才抛错。
- 写入成功后的读取失败、写入与确认读取均失败后重试。
- 真正子进程在发布凭据后 `os._exit`，随后恢复；两个真实 CLI 进程竞争同一提交锁。
- 快照缺失、冲突或凭据损坏，dry-run、暂停、只清匹配租约、游标无关字段保留。
- 恢复失败后的下一次预检仍可清旧租约并选择新批次；提交后更正来源保留为待整理。
- 报告子串不能代替整行标记，CLI 不再误报“游标保持原样”。

另在当前真实数据的临时副本中，对比旧版与新版选择清单一致，覆盖 12 条对话及 2 条偏好事件；只在副本注入故障、提交并恢复。真实人格、配置、三个任务、来信、核心记忆、游标、报告与对话数据库逻辑行均保持不变，没有向模型发送这些材料，也没有真实消费这批来源。

本机原生预检包装器通过 `runpy.run_path` 直接加载项目脚本，已核对指向当前文件。代码在下一次调用生效，不需要重启应用或服务，也不运行 setup_profile.py / setup_jobs.py。
