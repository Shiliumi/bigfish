# 来源与向量在同一事务内失效

2026-10-29 继续完善本地语义检索候选，解决 [独立缓存原型](semantic-cache-study.md) 在来源更正或遗忘后，要等下次缓存访问才移除向量的问题。此次仍仅修改开发候选和验证程序，正式应用未加载向量模型，也未给真实记忆库创建派生表。

## 为什么调整存储

[SQLite 的 ATTACH 文档](https://www.sqlite.org/lang_attach.html) 说明：WAL 模式下，多个数据库文件的事务分别原子，不能保证宕机时一起提交。先改来源、再清缓存，中间仍有故障窗口；交换顺序也无法解决迟到编码回写。

[Chronicle 固定版本的存储源码](https://github.com/indigokarasu/chronicle-agent-context-and-memory/blob/92e4351a852117a11542210d06e8e5bfb61c3f1a/engine/store.py) 在删除原始事件向量时，同时处理它的代理向量，提示需要检查所有派生层。本项目目前没有那些代理层，只需处理自己的来源与分块向量，没有复制或安装 Chronicle。

候选缓存因此改为 `episodes.sqlite3` 内的两个独立命名表：`fish_semantic_meta` 和 `fish_semantic_vectors`。原始经历、历史、FTS 和事项仍归 Journal 管理。向量是可重建的派生数据，但它们现在与原话共享一个数据库文件，**绝不能通过删除该数据库文件来清缓存**。

## 事务与写入约束

- 首次显式实例化 `SemanticCache` 才创建派生表、按来源编号的索引，以及两个持久 AFTER 触发器。普通 Journal 打开不会创建它们；正式适配器也没有导入候选缓存。
- 影响来源含义、身份、版本、别名或有效期的真实变化，会在同一个来源事务中删除对应向量。`OLD ... IS NOT NEW ...` 处理空值变化；FTS 的索引版本维护不触发删除。直接删除来源行同样清理向量，不依赖 Python 是否导入缓存模块。
- 面板的 JSON CLI 入口和聊天纠错都走 Journal；常规来源提交、缓存清理一起成功或回滚。清理出错时不会把遗忘报告成成功，原操作会报错并保留之前状态。
- 模型编码在事务外完成。发布向量时取得原库写锁，再验证当前来源；锁内其他写者不能同时更改来源。迟到结果仍需通过来源 revision、内容指纹、项目和模型身份检查；提交后的更改也会触发清理，交付文字前继续重读来源。
- 仍用新的只读连接查看已提交来源，避免混入调用方未提交的修改。健康缓存重开、准备和检索保持零逻辑写入；缺失或不一致的触发器在初始化事务中修复，并清掉可能漏失效的向量。
- 派生 schema 使用自己的 `schema=2` 元数据，**不修改原库的 `PRAGMA user_version`**。较新或不兼容的原库、派生版本均拒绝修改；等待写锁后会再次检查。旧原型的独立 `semantic-cache.sqlite3` 若仍存在，会拒绝继续，不静默迁移、保留使用或删除该文件。之前的临时回放库已自动清理，不需要迁移真实用户数据。

[SQLite 触发器文档](https://www.sqlite.org/lang_createtrigger.html) 说明持久触发器可作用于其他连接的写入，本实验也用另一个 Python 进程验证了这一点。当前触发器只处理自己的派生向量，不改变原有事项级联或历史保留规则。

自然到期与显式操作有所区别：时间流逝本身不执行 SQL。查询在到期边界就排除来源，并在下一次缓存访问清理向量；手动“标记过时”属于来源写入，会立即在该事务清理。没有新增定时器来追求精确到秒的删除。

这里的删除是数据库逻辑行删除，**不是磁盘取证擦除**。WAL、空闲页、备份、原始 Hermes 聊天、已发送给模型的上下文另有生命周期，不能声称已从所有介质撤回。

## 安全重建接口

开发代码可显式调用 `discard_cache(journal)`：在一个事务内按依赖顺序移除自己的触发器、索引和两张派生表，保留原始经历、历史、FTS、事项与原库版本。之后可重新实例化并编码。

它拒绝接管调用方尚未结束的事务，也拒绝不兼容版本或缺少归属标记的派生结构。移除中途失败会回滚；已有缓存句柄在结构移除后不再交付候选。这个函数没有挂到界面、聊天工具或自动任务上。

## 验证结果

```bash
python3 -m unittest discover -s scripts -p 'test_semantic_cache.py'
.setup/semantic-runtime/bin/python scripts/eval_semantic_cache.py --model-dir .setup/semantic-model --output .setup/semantic-cache-transaction-results.json
```

33 项标准库测试覆盖正常 Journal 的同步清理、并发读取提交前后状态、事务回滚、清理故障、其他进程删除、面板实际使用的 JSON CLI 路径、初始化期间原库版本变化、不完整字段拒绝安装、结构修复及安全移除。CLI 测试把公共脚本复制到临时项目运行，没有使用真实面板或私人数据库。

真实中文模型仍用之前固定的权重、三份虚构数据、56 条有效经历和 154 个查询。排序、门槛与模型均未调整；最新一次重跑结果：

| 检查 | 结果 |
| --- | --- |
| 缓存前五名与重新编码一致 | 154/154 |
| 固定补充门槛选择一致 | 154/154 |
| 原有词法召回与创建派生表前一致 | 154/154 |
| 更正、遗忘提交后，未访问缓存前 | 对应向量行已移除 |
| 生命周期断言 | 15/15 |

源记录逐项保持一致。页面增长不是精确的向量净占用量；查询编码仍另需约 3.62 ms，模型加载校验约 209 ms，完整实验峰值约 392.7 MiB。数字来自本机单次开发回放，不能外推大库性能或应用完整延迟。

此次没有调用付费 API，也没有用真实聊天进行生成测试。一致性保证不了相关性，原来会误联想的查询仍需改进。正式接入还要准备可移植的可选运行时、耗时上限及降级路径，并验证无关对象与否定关系；因此暂不新增设置或替换现有召回。
