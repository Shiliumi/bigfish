- [billion-context 的包入口](https://github.com/ranxianglei/billion-context/blob/master/package.json) 及 [DSH 压缩闸门源码](https://github.com/ranxianglei/billion-context/blob/master/src/agent/dsh-compaction-gate.ts) 说明它涉及宿主压缩管线与生命周期，而非可无条件叠加的提示。[Hermes 的历史问题 #64539](https://github.com/NousResearch/hermes-agent/issues/64539) 曾报告压缩摘要虚构用户消息，该 issue 已关闭，不据此认定当前固定版本仍有同一故障。继续保留 Hermes 自身的压缩链，后续以本机固定版本验证来源和说话人是否保留，不直接叠加代理。

## 已落地：1.14.1 回忆库读取路径

原先每个 `Journal` 构造都会运行建表语句、进入 `BEGIN IMMEDIATE`，并重写 `journal_meta.index_version`。因此即使只看回忆列表或查一段旧聊天，也需要拿写锁；其他连接正在写入时，纯读取可能等到超时。

改为先检查 SQLite 的 `user_version`、索引版本和当前来源版本。库已经初始化且派生索引一致时，不再建表、启动写事务或重写元数据。首次升级、老格式迁移和索引失配仍进入事务，拿到锁后复核状态，避免另一进程刚完成升级后再次修改。建表、字段迁移、派生索引及版本标记放在同一事务内；失败回滚并关闭连接。遇到较新结构版本时拒绝继续处理，不改其版本或日志模式。

没有改变召回排序、文字压缩、来源标记、纠错、别名、遗忘、持续事项或模型请求；读路径保持现有文件权限处理。这里的“零写入”指已初始化且索引一致时的 SQLite 逻辑内容，不是承诺不触及文件权限、WAL 辅助文件或系统缓存。老库首次升级、真正写入和索引修复仍需要写锁。

## 验证

在写实现前，新增的测试复现了纯读取写入元数据、被未提交写事务阻塞，以及初始化失败未关闭连接。实现后，新增五项检查全部通过，覆盖：

1. 连续打开与查询的 `total_changes` 为零，独立观察连接的 `data_version` 不变。
2. 其他连接持有未提交写事务时，读路径能读取先前已提交的来源，不暴露未提交修改。
3. 升级保留来源、更正、别名、历史和删除标记。
4. 更高结构版本原样保留并拒绝处理，包括原有非 WAL 日志模式。
5. 迁移异常回滚，连接确实关闭，错误数据保留供排查。

原有索引落后、旧版本摘要迁移、到期、遗忘、别名、异步回合以及持续事项检查继续通过。全部 Python 147 项、Node 63 项检查通过。

可重复的隔离对比：

```bash
python3 scripts/eval_journal_open.py --baseline 4acf160
python3 scripts/eval_memory.py
python3 -m unittest discover -s scripts -p 'test_*.py'
node --test ui/tests/*.test.mjs
```

`eval_journal_open.py` 为两版各建立相同的一百段虚构经历，打开和查询一百次，不读取实际聊天、不调用模型。2026-10-29 本机的一次结果：

| 检查 | 1.14.0 | 1.14.1 |
| --- | --- | --- |
| 每次纯读取的 SQLite 逻辑写入数 | 1 | 0 |
| 另一写事务未提交时读取已提交内容（测试超时 50ms） | 被写锁阻塞 | 可以读取 |
| 打开并查询的中位耗时 | 6.745ms | 6.521ms |
| 同一百个查询的召回文本 | 与新版逐字一致 | 与旧版逐字一致 |

无锁时的耗时变化很小，不宣称显著性能提升；主要收益是减少不必要的写锁争用。不是整个应用延迟、真实聊天质量或 token 节省率的测量。原有 91 问回放仍是目标首位 78/79、应留空 12/12；一个普通转述和三个深层转述仍漏召回，没有用本轮优化掩盖它们。
