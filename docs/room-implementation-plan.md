大肥鱼小屋实施计划

制定日期：2026-11-02；本次更新：2026-11-03。状态：实施中。1.17.0 已补齐阶段 2 的物品内容卡片和相册管理；阶段 3 只完成基础执行工具与环境接入，整个计划尚未完成。

| 阶段 | 当前实现 | 尚欠工作/验收 |
|---|---|---|
| 0 技术与素材 | 三维样片、透明角色、资源署名和分发 | 坐姿与家具关系、完整遮挡检查、资源/性能基线 |
| 1 场景与稳定性 | 房间、昼夜雨雪、真实活动来源、可见性暂停、窄窗口和图形恢复 | 一小时后台、真实系统睡眠、完整输入法、帧率与 CPU/内存测量 |
| 2 布置与照片 | 已实现并检查：移动/锁定/撤销、物品阅读与记忆卡片、收藏、聊天拍照、相册管理与导出 | 保留阶段 1 的长期验收依赖，不将短时检查算成长期通过 |
| 3 自主生活与记忆 | 已有：检查、移动、按请求拍照、执行回执和界面同步 | 灯光工具、带来源愿望、自主决策接入、重要共同变化入记忆、主动分享与来源失效联动 |
| 4 纪念物与关联 | 尚未实现 | 共同纪念物、来源引用、纠正/遗忘同步与关联视图 |

本轮验证见 [阶段 2 补齐](room-phase2.md)。此前验证见 [环境接入](room-presence.md)、[房间动作](room-actions.md)、[布置与照片](room-layout-photos.md)。

目标：在现有 macOS 应用中加入一间精致、可以互动的小屋，让大肥鱼的真实活动、兴趣和共同经历在画面中留下连续的变化。沿用现有聊天、桌宠、记忆、预算和来信系统，保持操作简单。

**技术路线与范围**

- 场景：React 内按需加载 Three.js，采用低多边形三维房间、有限角度相机、二维动画角色。先制作一间卧室，首批约 8–12 件家具，少量物品开放移动。
- 接入：沿用 Swift/AppKit + WKWebView、现有本地 Node 服务和桌面鉴权。新增“小屋”入口；布置工具点击后展开，小窗口改为底部抽屉。
- 人物：共用桌宠的活动来源；增加房间需要的站立、坐电脑前、休息等姿态。先验证素材与透明动画在 WKWebView 中的效果，再确定播放格式。
- 数据：房间布局、已执行动作和装饰偏好在本地保存。真实聊天、浏览与记忆继续由原有系统管理，房间通过引用读取，避免产生第二套事实库。
- 首版包含：昼夜、灯光、装饰性天气、人物状态、点击物品、有限布置、房间截图，以及少量有来源的生活变化。
- 后续扩展：共同纪念物、兴趣关联的小愿望、记忆关联视图。记忆星图不作为首版依赖。

**阶段 0：技术与素材验证**

交付：可在现有应用内运行的单场景技术样片，确认相机、灯光、人物叠加、素材许可和资源分发方式。

工作：

1. 确认依赖版本及其 WebKit 支持；选择有明确使用与再分发条件的家具和角色资源，记录来源。缺少合适资源时制作统一风格素材。
2. 验证房间与角色的尺度、地面接触、遮挡和透明边缘；单独验证坐姿与家具的位置关系。
3. 测试 Retina 清晰度、浅色与深色环境、窗口缩放、隐藏与恢复、休眠唤醒、图形上下文丢失后的恢复。
4. 记录当前应用的内存、空闲 CPU、聊天输入表现，作为后续对比基线。
5. 确定资源清单、校验与打包办法；大体积资源采用带校验的分发方式，避免把私人数据或无权分发的资源加入仓库。

验收：样片在真实 WKWebView 中运行；人物无明显白边、割裂、悬浮或异常遮挡；缩放无拉伸；渲染失败时有可恢复状态；打开样片不产生模型请求。

此阶段先确认最终路线是否达到视觉要求，发现透明动画兼容性问题时优先更换播放资源，不把低清静态头像作为最终交付。

**阶段 1：精致场景与稳定页面**

交付：可长期打开的小屋页面，具备房间、角色、昼夜灯光、基础天气与简洁交互。

工作：

1. 完成卧室、床、书桌、椅子、柜子、地毯、台灯及少量装饰；统一色彩、材质、阴影和尺寸。
2. 实现有限相机旋转、缩放与复位；正常浏览和布置状态使用清晰区分的交互，避免拖家具与转视角冲突。
3. 本地时钟驱动天色；天气先标为小屋氛围，支持手选。真实天气留待后续提供地点与数据来源后接入。
4. 接入现有 companion 状态：思考、浏览、处理任务、离线及来信。空闲小动作由本地规则驱动；睡姿属于角色表现，不推断用户是否睡觉。
5. 页面切走或窗口隐藏后暂停渲染；恢复时按最新状态恢复，防止累积计时器。页面与聊天状态隔离，动画不触发整页重绘。

验收：

- 从 520×420 最小窗口到常用桌面尺寸，主要操作可达，必要区域能滚动，面板不遮住关闭按钮。
- 聊天输入、中文输入法组合与滚动不受小屋更新影响。
- 后台至少 1 小时及一次睡眠唤醒后可恢复，布局和聊天草稿保留。
- 小屋关闭时无持续渲染循环、重复订阅或模型请求；对比基线记录实际资源开销。
- 在目标 Mac 上测量帧率，优先稳定 30fps，按测量结果调整阴影、粒子与分辨率上限。

**阶段 2：布置、物品与房间照片**

当前状态：以下六项已实现并通过本轮针对性检查，版本 1.17.0。长期后台、休眠等仍按阶段 1 留作待验，不据此勾选。

交付：布局可保存，能点物品查看实际内容，并能把当前房间画面发到聊天。

工作：

1. [x] 家具与可移动物品使用稳定 ID；定义可放置区域、朝向、边界、基础碰撞和用户锁定状态。
2. [x] 接入版本化布局保存、撤销最近一次布置、恢复默认布局。并发修改遇到版本变化时重新读取，避免覆盖用户刚做的调整。
3. [x] 先开放杯子、书、抱枕等少量物品移动；床、书桌等大件保留可靠交互位置。
4. [x] 点击电脑显示最近真实阅读与收藏；笔记本显示已有记录；缺少内容时显示空状态，避免模板示例被当成真实经历。
5. [x] 实现全景与窗边两个拍照位置；复用聊天图片展示，新增受鉴权保护的本地图片读写和生命周期管理。
6. [x] 只有拿到当前有效场景和布局版本时才返回新照片。窗口关闭时先唤起本地渲染；无法完成时明确失败，不用旧图冒充刚拍的照片。

验收：重启后布局不丢失；物品不能放出房间或明显互相穿插；失败动作不改变存档；照片与指定布局版本一致；截图不包含其他窗口、密钥或调试信息。

**阶段 3：兴趣驱动的生活与共同记忆**

交付：她能在合适的时机调整少量物品、表达有来源的愿望，并在以后聊天中记得这些变化。

工作：

1. 定义受约束的房间动作：检查物品、移动允许的物品、切换灯光、拍照、提出愿望。每个动作具有唯一请求 ID 和执行回执，重复请求不会重复搬动或发消息。
2. 模型提出动作后由本地服务检查并执行；聊天中的“已经做了”必须依据成功回执。用户锁定的物品、无效目标与过期布局不能执行。
3. 房间决策优先合并到现有聊天或真实冲浪结束环节，不新增独立的定时模型任务。只提供简短房间摘要和少量相关兴趣、记忆引用。
4. 兴趣必须有可追溯的阅读或对话来源；待实现的愿望与已经发生的事件分开保存。设置数量、过期、重复合并和冷却规则。
5. 记录重要的共同变化，例如用户明确喜欢暖光、一起确定的物品位置。纯待机动作与反复挪杯子不写入长期记忆，也不直接改写 SOUL 或成熟人格偏好。
6. 房间行为沿用现有来信的安静时段、打扰与预算控制；动作完成不等于必须发消息。一个事件在聊天、桌宠和来信之间统一去重。
7. 关联记忆被更正、失效或遗忘后，房间及时停止展示旧事实；保留装饰外观与继续引用旧记忆分别处理。

验收场景：

- “把杯子挪到窗边”执行成功后，画面、存档与回答一致；重复回调不会再次移动。
- 用户锁定杯子后，她的自动调整无法覆盖该设置。
- 她实际阅读某类内容后，才产生相应的收藏或愿望；没有来源时不编造阅读经历。
- 用户问“刚才在干嘛”，回答引用实际活动记录，必要时给出当前房间照片。
- 隔天仍能接上共同决定的布置；更正或遗忘相关记录后，不再当作有效事实引用。
- 达到预算限制或无模型可用时，房间仍可打开、布置和播放本地动画，停止新增模型决策。

**阶段 4：纪念物与记忆关联展示**

交付：在稳定运行的小屋中加入少量共同纪念物，并在现有记忆空间提供可追溯的关联视图。

工作：先用收藏卡片和纪念物呈现真实事件；后续按同一话题、事件或明确引用构建关联。连线标明依据，节点支持查看来源、修正与遗忘。只有用户需要浏览复杂关联时再增加三维星图；不展示无法解释的“人格成熟度”或记忆百分比。

验收：每个纪念物有来源；关联可解释；删除或修正记忆后视图同步；默认页面仍简洁，图谱不影响聊天与小屋性能。

**实现边界与模块安排**

| 模块 | 建议位置或接入点 | 职责 |
|---|---|---|
| 房间入口 | `ui/src/App.tsx` | 按需加载、导航与页面生命周期 |
| 场景与控件 | 新增 `ui/src/room/` | 渲染、相机、动画、点击与布置 |
| 房间本地服务 | 新增 `ui/server/room.mjs`，接入现有 `index.mjs` | 统一状态、布局版本、动作校验、照片回执 |
| 运行状态 | 现有 `ui/server/companion.mjs` | 向桌宠与小屋提供共同的实际活动来源 |
| 私人房间数据 | `data/room/` | 布局、回执、待办愿望、私有照片；沿用 gitignore |
| 公共资源 | 小屋资源目录及来源清单 | 模型、材质、动画、许可、校验与版本 |
| 记忆和兴趣 | 现有 journal、curiosity 与来信服务 | 提供受有效性约束的引用，接收有意义的已发生事件 |

建议接口分为状态查询、布局修改、受约束动作和照片请求。所有入口沿用桌面会话鉴权与跨站请求限制，不把本地文件路径、任意命令或任意网络请求暴露为房间动作。

状态由服务端统一管理；渲染页面只保存临时视角和交互状态。已执行动作包含动作 ID、布局版本、结果与时间；记忆引用包含来源 ID 和修订信息。先稳定这些契约，再接入模型工具。

**Token 与运行成本验收**

- 打开、空闲、昼夜变化、物品点击、手动布置、截图和基础待机动画新增模型调用数为 0；使用请求审计验证。
- 只有需要自然语言理解或自主选择的交互进入模型；优先复用现有请求，不发送整份聊天或记忆库。
- 房间相关请求与现有预算统一计量，记录输入、输出与缓存用量。根据实际测试数据决定是否开放更多自动行为，不预先声称固定节省比例。
- 无真实内容时少做变化，预算不足时保留本地交互；不以反复唤醒模型维持“活跃”。

**验证、发布与顺序**

先完成阶段 0 和阶段 1 的可体验版本，再进入行为培养。阶段 2 是阶段 3 的前置条件：执行和持久化可靠后，才让模型操作。阶段 4 独立排后。

每阶段只增加必要验证：状态转换、持久化、并发版本冲突、动作幂等、来源失效、预算与消息去重使用针对性测试；视觉、输入法、遮挡、后台恢复与图形兼容性在真实 macOS 应用中验证。保留现有聊天、桌宠与记忆相关检查。

正式更新前备份相关私人状态；新增功能采用可关闭的入口，关闭后不影响原有应用。每阶段交付可体验版本、实际验证结果和已知限制。发布前检查素材许可、公开资源清单和 gitignore，只提交公开代码、文档及获准分发的资源。

前置记忆采集身份修复已独立验证、安装并提交，适配器版本为 1.6.14；小屋使用独立提交记录，后续继续分别验证。
